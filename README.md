# n64-recomp-toolkit

Pinned, built copies of every tool needed to statically recompile an N64 ROM into a native
Linux program with [N64Recomp](https://github.com/N64Recomp/N64Recomp), plus ROM inspection
scripts and a `new-game.sh` that starts a project for any ROM. Nothing here is specific to one
game, and the toolkit folder never holds a ROM or anything derived from one.

Clone it anywhere: every script finds the toolkit from its own path. Used by [Aidyn ReChronicled](https://github.com/spitzdano/AidynReChronicled), the first
port made with it.

> **AI disclosure.** This toolkit was built with AI assistance (Claude Code), directed by spitzdano.

## Setting up a machine

```sh
./install.sh          # system packages; lists what's missing and asks before sudo (safe to rerun)
./build.sh            # .venv with pinned splat, N64Recomp + RSPRecomp -> bin/
./runtime-check.sh    # builds N64ModernRuntime and RT64 once in a scratch folder, then deletes it
./doctor.sh           # checks every tool runs and prints its version
source ./env.sh       # puts bin/, scripts/ and the venv's python3 on PATH
```

`tests/run.sh` checks the scripts end to end on a synthetic ROM (header bytes and a few
hand-written instructions, no game data) and deletes everything it made.

## Layout

| Path | What |
|---|---|
| `install.sh` | System packages, Arch or Debian/Ubuntu (see below) |
| `build.sh` | Creates `.venv` from `requirements.txt`; clones and builds `src/N64Recomp` |
| `runtime-check.sh` | Proves N64ModernRuntime and RT64 build here (log: `runtime-check.log`) |
| `doctor.sh` | Checks every tool runs and prints its version; warns when a system package drifted from `VERSIONS.md` |
| `env.sh` | `source` it (bash or zsh) |
| `pins.env` | Every pinned source commit, with the reason for each |
| `requirements.txt` | Every pinned Python package (splat64[mips] and its dependencies) |
| `VERSIONS.md`, `versions.lock` | Generated by `scripts/record-versions.sh`; don't edit |
| `bin/` | `N64Recomp`, `RSPRecomp` (built) |
| `src/N64Recomp/` | Source checkout at the pinned commit |
| `patches/` | Local fixes on top of the pin, applied by `build.sh` from a clean tree each build: `n64recomp-conditional-traps.patch` recompiles `teq`/`tne` (GCC's divide-by-zero checks) as a conditional `do_break`; `n64recomp-stale-jtbl-base.patch` finds GCC jump tables whose dispatch blocks follow one another (the index register still held the previous table's pointer) |
| `scripts/` | The tools below |
| `template/` | What `new-game.sh` copies into a project, with `__PLACEHOLDERS__` |
| `shell-template/` | The runtime shell from the first port: `files/` (`src/`, `CMakeLists.txt`, `tools/build_game.sh`) goes into every new project; `optional/` holds a Controller Pak and RT64's texture hash, added by hand (see its README) |
| `docs/porting-notes.md` | What the first port taught: split problems, hooks, calling game code, extended GBI, texture packs, interpolation, testing without a person |
| `tests/` | Synthetic-ROM tests for the scripts |

## Tools

| Command | Does |
|---|---|
| `rominfo.py <rom> [--json]` | Byte order, size, SHA-1, internal name, game code, version, header and real entry point, CIC (from splat's own code), and warnings for things the standard path can't handle |
| `romconvert.py <in> <out.z64>` | `.v64`/`.n64` to big-endian `.z64`; never overwrites its input or an existing file |
| `ucode_scan.py <rom> [--json]` | RSP microcode version strings and their ROM offsets (a hint, not proof) |
| `new-game.sh <rom> <name>` | Scaffolds `~/Work/<name>-recomp` (or `$N64RECOMP_PROJECTS/<name>-recomp`) |
| `record-versions.sh` | Rewrites `VERSIONS.md` and `versions.lock` |

### `new-game.sh`

1. Runs `rominfo.py`. A byte-swapped or little-endian dump is refused with the `romconvert.py`
   command to fix it.
2. Creates the project folder (refuses one that exists), symlinks the ROM in as `baserom.z64`
   (never copies it), writes `rom.sha1` and `rominfo.json` (header fields and hashes only).
3. Runs `python3 -m splat create_config` and moves its yaml to `split/<name>.<region>.yaml`,
   pointed at the project layout (`split/asm`, `split/bin`, `build/`). For a game with a decomp,
   replace that config with the decomp's: it knows the layout far better.
4. Copies `template/`: `tools/split.sh`, `tools/build_elf.sh` (assemble, link, pad, compare with
   the base ROM, name the segment of the first difference), `tools/recomp.sh`,
   `tools/check_recomp.sh`, `tools/find_fallthrough.py` and `tools/find_missing_funcs.py` (split
   problems), skeleton `<tag>.toml` and `aspMain.<region>.toml` with every key the
   recompilers read, a `.gitignore` covering ROMs and generated code, and a README stub. Then
   `shell-template/files/`: the runtime shell (`src/`, `CMakeLists.txt`, `tools/build_game.sh`)
   with the executable `<Name>Recomp`, the window title from the ROM header and the ROM's
   XXH3 hash (`xxhsum -H3`) filled in. If
   create_config named the entrypoint's target `main`, the toml's `renamed` lists it: a C function
   called `main` with N64Recomp's signature doesn't compile, and N64Recomp only renames libc names.
5. `git init`, then adds N64ModernRuntime and RT64 as submodules at the `pins.env` commits and
   copies the runtime's GPL-3.0 text to `LICENSE`. Nothing is committed.
6. Prints a warning for each sign the game needs more than the standard path: unknown CIC,
   entry point outside KSEG0 (TLB-mapped code), Yaz0/Yay0/MIO0 headers (compressed code or
   overlays), a non-traditional entrypoint.

## What "any ROM" means

The toolkit gets any game as far as recompiled code that compiles. Getting from there to a working
port is per-game work: the splat config, symbols, microcode and save hardware. Some games need more
before that: compressed code (decompress the ROM first, as Zelda64Recomp does), relocatable overlays
(`relocatable_sections_path`), or TLB-mapped code, which N64Recomp doesn't handle yet.

## System packages

`install.sh` knows Debian/Ubuntu and Arch. The package names map like this:

| Debian / Ubuntu | Arch | Notes |
|---|---|---|
| `binutils-mips-linux-gnu` | `mips-linux-gnu-binutils` | **AUR**, built by yay from the GNU tarball (sha512-checked). `--nocheck` skips binutils' own test suite. |
| `python3`, `python3-venv` | `python` | venv is built in |
| `git`, `cmake`, `clang`, `lld`, `llvm` | same names | |
| `ninja-build` | `ninja` | |
| `libsdl2-dev` | `sdl2-compat` | SDL2 API on SDL3; headers and `sdl2.pc` included |
| `libgtk-3-dev` | `gtk3` | headers included |
| `vulkan-tools` | `vulkan-tools` (+ `vulkan-icd-loader`) | |
| `xxhash` | `xxhash` | `xxhsum -H3`: the ROM hash librecomp checks |
| (implicit `build-essential`) | `base-devel`, `pkgconf` | also needed to build AUR packages |
| GPU Vulkan driver | `nvidia-utils` / `vulkan-radeon` / `vulkan-intel` | checked, not installed: it depends on the GPU |

## Pins

See `VERSIONS.md` for the full list. Notes:

- **Location.** `new-game.sh` puts projects in `~/Work/<name>-recomp` unless `N64RECOMP_PROJECTS`
  says otherwise. Every script finds the toolkit from its own path, so the folder can live anywhere.
- **N64Recomp `ffb39cd`** and **N64ModernRuntime `cdf5abb`** were both the heads of their repos on
  2026-10-14.
- **RT64 `5473732`**, not Zelda64Recomp `dev`'s `23cab60`. `23cab60` is on a pre-Plume side branch
  of RT64 that builds with `-Werror` and fails under clang 22 (a new
  `-Wuninitialized-const-pointer` warning in its bundled imgui). `5473732` (main, 2026-08-02) is
  what Zelda64Recomp's `recomp-frontend` branch builds with, next to N64ModernRuntime `589bbf0`,
  one commit before ours. RT64's newest head was under 48 hours old.
- **Reference shell.** For bringing up a game's runtime and renderer, Zelda64Recomp `recomp-frontend` @ `ab0fcb5` matches our
  runtime and renderer far better than `dev` @ `b65c482`, which uses an older runtime
  (`df7e820`) and the pre-Plume renderer.
